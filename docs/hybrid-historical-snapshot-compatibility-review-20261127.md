## Metadata: what exists and what it proves

| Stored layer | Existing identifiers/evidence | Can it distinguish the discount revision? |
| --- | --- | --- |
| Normalized saved Hybrid request | `policy_version=HYBRID_PROMOTION_V1`, channel ONLINE, ordered selections, rates and optional replacement intent | No. Both implementations accept the same request. `HybridInvoiceRequest::normalize()` whitelists fields; there is no discount-revision selector. |
| Saved calculation | Same policy; `rounding_version=HYBRID_CENTS_V1`; `invoice_allocation_policy=INVOICE_PERCENT_V1`; replacement policy/mode and immutable offer/price revisions | No. Offer/price identity and allocation algorithm do not identify which lines were invoice-eligible. |
| Review | Policy, configuration/control versions, actor/customer/source/date/payment evidence, `unit_allocation_version=HYBRID_UNITS_B1_V1`, allocation digest, review hash | No guaranteed revision discriminator. Configuration/control versions are environment/state identifiers without an established one-to-one rule mapping. Dates are not trustworthy release boundaries. |
| Snapshot and seal | `snapshot_version=HYBRID_SNAPSHOT_V1`; SHA-256 canonical digest; line/segment/run counts; allocation version | Same values under both rules. A digest identifies the particular content, not an algorithm revision unless independently mapped to one. |
| Typed storage | Migration 025 constrains policy/rounding/allocation identifiers to the same values and stores configuration version, amounts, review hash, JSON, child rows and seal | No separate eligibility revision column is present. Do not modify migration 025 or backfill immutable records to invent one. |
| New Stage 5 fixture envelope | `invoice_discount_eligibility=UNPROMOTED_LINES_V1` in future `stage5Prepare()` output | Test-artifact provenance hint only. It is outside the invoice seal and absent from earlier artifacts, including possibly current-rule artifacts. It is not financial authority or an application-version field. |

`HybridInvoiceRequest::digest()` is unkeyed SHA-256 over canonical JSON (sorted object keys, preserved list order), not a digital signature or HMAC. Review/allocation/seal hashes detect content changes relative to a retained trusted digest; they do not prevent an attacker with full write access from replacing content **and** every hash. SQL immutability, physical projection checks, authorization and separately trusted provenance remain essential. Worker transport authentication must not be mistaken for an invoice signature. No Hybrid offline signature is shown here; Hybrid requests are explicitly rejected offline. Existing signed legacy drafts remain outside this proposal.

**Answer to safe discrimination:** existing version fields alone cannot identify the issuance era. Exact full-content validation under two pinned known algorithms can identify a compatible mathematical interpretation without relying on totals alone, but cannot independently establish who issued it or when. Cases such as invoice rate zero can be identical under both rules; report them as compatible/equivalent, not definitely historical or current. Unknown provenance cannot be repaired by assuming 675 means old or by setting an artifact marker.

## Recommended version-aware design (not implemented)

1. **Keep forward calculation current-only.** Leave the approved eligibility math intact. Add a server-owned explicit calculation revision to future sealed review metadata, for example `review.calculation_revision=HYBRID_INVOICE_ELIGIBILITY_V2`. Do not accept browser-selected historical revisions or permit a legacy evaluator in new preview/issue. Include the revision before review hashing and sealing; enforce it at new persistence boundaries. This can retain existing outer policy/rounding/allocation IDs if storage constraints remain valid; confirm JSON/consumer contracts before implementation. It is a semantic revision, not a replacement for the snapshot format or allocation version.
2. **Pin a read-only historical evaluator.** Preserve the exact pre-correction behavior in a narrowly scoped pure compatibility service, including product/replacement calculations, strict cap, decimal/string operations, rounding, order and segment allocations. Candidate source is `app/Services/HybridPromotionPolicy.php` at HEAD above, Git blob `cddfcd862909f096f06a26d7e80a626ce3d44916`. Its invoice allocation includes every post-product/replacement payable. Review its dependencies (`InvoiceDiscount`, `BenefitPolicy`, `PromotionCalculator`, `HybridUnitAllocations`) and freeze their required behavior too; merely copying the old top-level method is insufficient if helpers later change. This source pin does not prove every historical invoice used that exact implementation.
3. **Separate sealed-read validation from construction.** Persisted reads must require a complete seal and recognized structure. Check bounds, canonical review hash, original allocation digest, original seal digest/counts and supported versions before interpreting amounts; reject malformed/unsupported content. Construction may validate a not-yet-sealed server-generated snapshot separately. Do not add defaults, new metadata or inferred versions inside old JSON before hashing. Keep the current canonicalization for old snapshots byte-for-byte semantically compatible.
4. **Dispatch strictly.** For future explicitly marked snapshots, use only the named recognized evaluator; an unknown marker fails closed, and a marker/math mismatch cannot fall back to another rule. For already-issued unmarked V1 snapshots, evaluate only an allowlisted legacy-stacking candidate and the current-eligibility candidate from immutable inputs. Compare **every** calculation field, line/segment component, findings, original ordering, cap result and complete unit-run allocation/digest to the saved content. One full match validates that interpretation. Two full matches are equivalent for this record and need no invented issuance-era classification. No match rejects with a compatibility finding. Avoid unlimited "try old versions until something passes" logic. No amount-based or date-based heuristic is allowed.
5. **Validate originals; do not replace them.** After a successful match, continue using the saved calculation and saved allocation runs for reads, settlement, documents and return history. Keep the reader's typed-row/official-money/identity and actual payment/stock reconciliation. Derived interpretation status may be returned outside the sealed body, without changing historical JSON or digest. Optional future authoritative invoice-to-revision attestations must be separately approved, append-only and bind invoice identity plus the existing trusted seal digest; do not create them based only on a matching total.
6. **Preserve trust limits.** If independent stored seals/backups/audit evidence cannot establish provenance, report that limitation rather than claim cryptographic authentication from self-consistent hashes. No historical re-signing, re-sealing or rewriting is required for a legitimate old snapshot: unchanged canonical content must reproduce its original hashes, and its original algorithm must reproduce its original allocations. The current bug invalidates the interpretation, not the original bytes. Existing signatures, if any exist outside the inspected scheme, require their original verification path/keys; never replace them with a new SHA hash.

The unmarked compatibility path is read/replay-only. A pending old forward review must be refreshed under current rules before a new issue, whereas a previously accepted command must replay its original result and identities. Keep command payload hashes, request UUIDs, initial receipt values and return fingerprints unchanged. A code-version change must not silently change an accepted operation.

## Historical financial and stock requirements

- For a genuine old 675 invoice paid 675, debt remains zero; do not create a 75 receivable. Its old invoice discount 75 and original unit cents remain intact. A current 750 invoice must continue using zero invoice discount on Glucose.
- Repeated old remainder returns credit 67.50 each, then an old qualifying unit 90; current values are 75,75,100. Three-unit totals are 225 versus 250. Residual five-unit void credits are 450 versus 500. The free recovery threshold/actual delivered quantity remains the original offer's rule, independent of monetary revision.
- Replay accepted old return plans against their stored original positions and cash-at-return basis. Preserve ordered cursors, no overlap/reuse, revision and terminal-void checks, original replacement allocations, retained 50% cap and custody conditions. Do not reprice retained goods or claw back benefits using today's rule. An old retained-cap failure remains a failure even when the revised forward policy would have allocated no invoice money.
- Payments remain posted actual collections only, excluding change. Debt-first credits and cash-backed Refund Due use original invoice net and accepted prior credits. Example: old net 675, cash 575, two-unit credit 135 => debt reduction 100/refund 35; current net 750, cash 650, credit 150 => 100/50. Preserve noncash and legacy-void conflict blocks; physical refunds remain unavailable.
- Preserve all official invoice/payment/stock/sync IDs, source location, paid/free stock deductions and equal/equivalent physical return movements. Compatibility validation performs no posting or projection repair. Receipt generation must reproduce original amounts and identities; reports must keep original financial components distinct from later collections, linked credits and liabilities. Never present old historical promotion allocations as instructions for a new sale.

The document suite can block the preparation chain after creating records; do not run it unchanged or bypass its checks.

Recommend two explicit synthetic cohorts: frozen, provenance-documented legacy snapshots/return plans with original seal and expected cents; and fresh-current fixtures with server-stamped revision plus generator revision/hash. Use separate new artifact names/directories and preserve archived artifacts. Choose document/report expectations from the approved cohort and verified sealed interpretation together, never from an untrusted envelope marker or from amounts alone. A missing marker is **unknown**, not proof of legacy. The current reporting fallback preserves old expected literals but does not resolve provenance and must not be treated as automatic authorization to run unmarked artifacts. Do not stamp existing artifacts to make tests pass. A later authorized inspection must bind fixture IDs, sealed content, generation source and independent evidence; none has occurred here.
